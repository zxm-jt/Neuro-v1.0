## 一、问题陈述

**谁**：一名学生，把 Neuro 当作每天长时间开着的桌面语音伙伴（英文人设、称呼用户 user）。

**什么场景**：一边写题/查资料一边用语音跟她说话，双手常占用键盘鼠标，期望像跟真人同桌聊天一样自然来回。

**现在的解决方式与为什么不行**（均为项目日志实锤，非猜测）：

| 现象（用户原话） | 真实根因（已定位） | 证据 |
|---|---|---|
| 「不等我说完就开始说（抢话）」 | 端点判定只靠静音阈值 + 语义裁决规则，对"句中思考停顿"无区分能力；且 `_pickTokenBudget` 的抢占式生成让首字过早输出 | `00_问题总结.md` §1、§10 |
| 「无法打断她说话」 | `config.json` 里 `suspend_mic_while_tts: true` **在 TTS 播放期间直接挂起麦克风** → 物理上无法打断；另有 `set_tts(False)` 的 0.8s 保护期吃掉插话开头 | `config.json:71`；`03_...md` §七 |
| 「语音识别能力差 / 突然变差」 | 0.3~0.8s 碎片被单独送去 SenseVoice → 输出日文假名垃圾并乱判语种；WS 半开后退回低质量 POST 路径 | `03_...md` §三 |
| （新需求）角落里的她"看不见"我屏幕 | 现有 `vision` 只有单张截图 + 手动触发，常开视觉未接线 | `config.json:46-74`（`vision.free`） |

**一句话结论**：这不是"再加功能"的问题，而是**把"听—想—说"这条实时链路的时序控制权还给用户**的问题。时间轴（谁在什么时候说话）比模型大小更决定体验。

## 二、目标用户

- **主要用户（唯一 P0 用户）**：学生 / 重度桌面前用户；英语交流为主、偶尔夹中文；非技术用户，但有调参意愿。
  - 技术水平：会改 `config.json`，不看源码。
  - 核心诉求：**长时间陪伴的语音自然感** > 功能丰富度；对"卡顿、抢话、答非所问"零容忍。
- **次要用户**：其他想用 Neuro 练口语 / 找桌面陪伴的学生党（人设可迁移）。

## 四、我们的差异化

1. **"不抢话"要量化到可验收**——竞品普遍靠固定静音阈值，我们以**语义端点 + 双下限/上限时间窗**定义（见 §六）。豆包已验证"动态判停"能降 40% 抢话，这是方向正确的行业共识。
2. **本地 Live2D + 反逻辑声纹（她自己的声音可白拿）**——比 Desktop Mate / 肉派派的回声与误触发问题天然更稳。
3. **屏幕感知是"主链路"而非外挂**——应用一打开就本地抽帧 + 变化检测（隐私、零成本）+ 免费视觉理解（GLM-4V-Flash）做「没有证据就继续看」，对标 Loona DeskMate 未兑现的承诺。
4. **专为单一重度用户调优**——不做通用助手，允许激进的人设化与延迟预算分配。

## 六、MVP 范围（仅 F1–F4）——可验收的语音体验指标（EARS）

> 格式：While/When/If + 系统必须/应该 + 行为。所有数值为**可测默认值**，允许架构师在评审中微调，但**必须保留"下限 + 硬上限"结构**。

### F1 端点判定（不抢话）

- **EARS-V1（核心·不抢话）**：While 用户在**句中非完整语义停顿**（未出现句尾语调下降 + 末词为连词/介词/填充词，如 "and…" "我…那个…"），系统**必须**保持聆听，**不得**在停顿后 1500ms 内启动 LLM 生成或 TTS 播报。
- **EARS-V2（快速响应）**：When 系统判定用户**语义上已说完**（句尾语调下降 / 语法与语义完整），系统**应该**在 **≤500ms** 内开始响应。
- **EARS-V3（硬上限兜底）**：If 端点模型持续认为"用户可能还没说完"，系统**必须**在累计静音达到 **3000ms** 的硬上限时强制提交当前轮次，**绝不**无限悬挂。
- **EARS-V4（下限保护）**：系统**必须**对任何轮次结束判定施加 **≥300ms** 的最短静音下限，防止句首被切。
- **EARS-V5（语气词不打断自己也不误判）**：While 用户发出纯反馈语气词（"mm-hmm" "yeah" "哦" "嗯"，时长 **<300ms** 或命中反馈词表），系统**必须**将其视为"继续聆听"信号，**不得**打断自身正在播放的语音，**也不得**据此开启新轮次。
- **EARS-V6（自适应）**：系统**应该**按用户近 **N=20** 轮的实际"思考停顿长度"自适应调整下限，使"过早抢话"与"响应迟钝"两类投诉同时下降（以会话样本统计口径验收）。

### F2 真打断 / Barge-in

- **EARS-B1（可打断的前提）**：While TTS 正在播放，系统**必须**保持麦克风采集开启（**移除 `suspend_mic_while_tts` 的"硬挂起"语义**），并启用回声消除（AEC）。
- **EARS-B2（打断响应速度）**：When 用户在 TTS 播放中说出**有实质内容的语音**（非 <300ms 反馈语气词），系统**必须**在 **≤150ms** 内让本地播放静音；**必须**在接收到模型打断信号前**先本地停播**，不得等网络往返。
- **EARS-B3（有实质内容才打断）**：If 用户输入被判定为纯反馈语气词或时长 **<300ms** 的短音（咳嗽、椅子响），系统**必须**不打断当前播报。
- **EARS-B4（回声自激防护）**：While TTS 播放且用户未佩戴耳机，系统**必须**通过声纹/回声判定拒绝"自己的声音"触发打断，避免自激（复用现有反逻辑声纹）。
- **EARS-B5（打断后可续接）**：When 发生打断，系统**必须**保留被打断的**已生成未播报**内容，并在下一轮以"不重复已播部分"的方式续接；已播部分**必须**计入对话历史。
- **EARS-B6（打断取消上游）**：When 用户打断且随即给出新指令，系统**应该**尽力取消/降级被中断的上游生成，避免多次打断累积多个在跑的请求（当前为已知限制 L1）。

### F3 识别质量保底

- **EARS-A1（碎片不单独识别）**：系统**必须**将时长短于 **800ms** 的语音碎片合并进相邻段再送识别（沿用现有 `SHORTCUT_MIN_S=0.8`），**不得**单独送 0.3~0.8s 碎片给 ASR。
- **EARS-A2（垃圾丢弃）**：If 合并后仍无法获得可信上下文（缓冲已滚动、补不到真实音频），系统**必须**丢弃该片段，**不得**将乱码/他语种（如日文假名）结果送入 LLM。
- **EARS-A3（回环拒绝）**：系统**必须**拒绝与"她自己的声纹"相似度高于阈值的输入（现有 0.72），其余一律放行（**不得**因缺少声纹档案而误拒用户）。
- **EARS-A4（语种一致）**：系统**必须**保证送进 LLM 的文本与回复语种策略一致（英文人设下，任何出口文本不得残留中文字符影响播报声线）。
- **EARS-A5（链路自愈）**：If 流式链路半开/断开，系统**必须**在 **≤3s** 内检测并恢复，**不得**静默退回低质量识别路径超过 **5s**。

### F4 连续屏幕感知

- **EARS-S1（抽帧节奏）**：While 屏幕感知启用，系统**应该**以 **1 fps** 默认频率本地抽帧（可配），变化不显著时（帧间相似度 ≥0.82）**必须**不产生新观察。
- **EARS-S2（主动沉默）**：If 当前帧没有足够重要的视觉更新，系统**必须**能输出"继续观察"而不生成空话（对标原实时视觉方案的主动沉默机制）。
- **EARS-S3（隐私边界）**：While 屏幕感知运行，系统**必须**仅在本地抽帧；上传视觉内容**必须**显式可关；**必须**不采集原始输入内容/密钥等隐私数据。
- **EARS-S4（可随时提问）**：When 用户对屏幕内容提问，系统**应该**基于最近一帧/最近观察上下文作答，而非要求用户重新截图。

## 七、边界条件

- **空状态**：会话开始尚无用户输入 → 不主动抢麦、不误触发。
- **错误状态**：ASR 返回空/乱码 → 丢弃并静默，不输出错误话术（避免"答非所问"）。
- **加载状态**：上游 LLM 慢时 → 用等待语气/表情占位，而非空播或提前抢答。
- **边界值**：静音时长卡在 300ms/3000ms 边界 → 取"继续聆听"（保守）。
- **并发**：用户连续打断 3 次 → 上游请求必须被取消/合流，不得排队拖垮主链路（见 L1）。
- **离线**：无网络时 → 本地语音链路与屏幕抽帧仍工作，视觉增强降级。
- **权限拒绝**：麦克风/屏幕录制权限被拒 → 明确提示入口，不静默失败。

## 八、主要风险与待架构师决策项

1. **语义端点检测的实现成本**：是否引入类 LiveKit turn-detector 模型？英文可用、中文缺失。需架构师评估"自研小分类器"vs"规则+语调"vs"训练数据可得性"。
2. **上游不可取消（L1）**：DeepSeek 流式是否支持服务端取消语义，需架构师核实；否则需二段式预算方案。
3. **AEC 与 `suspend_mic_while_tts` 的取舍**：去掉硬挂起后回声自激风险由谁扛（声纹 vs AEC）。
4. **屏幕抽帧的隐私与资源占用**：1 fps 是否会像 Desktop Mate 那样被投诉 CPU 占用。
